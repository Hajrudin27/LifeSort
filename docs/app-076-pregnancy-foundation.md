# APP-076 — Pregnancy foundation (Phase A and B1)

Pregnancy is internal-only. Phase A delivered contracts, a forward-only server schema, RLS/RPC boundaries, registry classifications and tests. Phase B1 implements only the protected local substrate: a separate AES-GCM ciphertext at `lifesort-pregnancy`, its own SecureStore key/AAD, and a validated greenfield `PregnancyProtectedStateV1` containing canonical local state, durable encrypted mutation intent, cursor, technical consent metadata and payload-free tombstones. One ciphertext replacement is the application-level state-plus-intent commit boundary; it is not a claim of formal storage-engine fsync or power-loss transactions. Registry maturity remains a hard ceiling: a remote flag can restrict Pregnancy but cannot promote it into public discovery or creation.

`pregnancy.user-health` is Profile B. Its actual blob/key/AAD are now registered as **implemented**. The existing plaintext outbox continues to reject Profile B. The B1 encrypted queue is embedded in the same Pregnancy ciphertext; no separate queue key or plaintext fallback exists. B2 must still implement client transport, coordinator injection, pull/reconciliation and recovery UX before any product flow is exposed.

The implemented server contract is a single authenticated static command for roots, logs, appointments and settings. It serializes commands per account, allocates monotonic `change_seq` records, and returns bounded metadata-only cursor pages. The sequence—not a timestamp—is the incremental-pull correctness key. Receipts hold only request hashes and safe acknowledgements; changes hold only reconciliation metadata. Deletion scrubs health payloads and root deletion tombstones/scrubs children with their own change records.

Consent is fail-closed against a server-controlled supported/current policy configuration. No production Pregnancy policy is seeded here, so production writes remain blocked until an approved policy migration/process configures one. Withdrawal is per purpose and withdraws every active consent of that purpose, so a retried or second-device grant cannot keep authorising writes. It blocks every consent-gated upsert, including recovery-state writes, and never the owner-bound pull, read or delete paths. The policy configuration itself is not readable or writable by clients.

Phase B1 owns encrypted local storage, encrypted queue implementation and cleanup lifecycle. B2 still owns client coordinator/rebaseline transport and consent UX. The Phase A separate-queue seam was removed because it could not guarantee an atomic state-plus-intent commit; the encrypted Pregnancy repository is the only queue boundary and has no plaintext fallback.

Consent withdrawal stops all Pregnancy upserts and cloud recovery-state writes until a current supported consent is granted again. Owner-bound reads, pull for presentation/deletion, delete, account deletion, consent inspection/withdrawal/re-grant, and local-only recovery UX remain allowed. The idempotency request hash intentionally includes `consent_id`: a mutation id cannot be rebound to a later consent after withdrawal/re-grant. Receipts contain no raw payload, but their deterministic unsalted digest may permit low-entropy inference to a sufficiently privileged database reader; this is an internal Phase-A residual that must be resolved in Phase B security/privacy sign-off before beta/public availability.

The TypeScript contracts model live entities only. Scrubbed server tombstones need explicit reconciliation variants in Phase B. v1.1 leaves notes and outcome notes unbounded; no product/medical length limit is invented here.

Launch remains blocked on legal/privacy consent review, DPIA, Supabase DPA/region confirmation, clinical sign-off, intended-purpose review for any escalation, APP-097 portability, external store/marketing review and physical iPhone QA.

Server validation is exactly: entity type and operation; revision; the symptom enumeration (v1.1 §4.2); the weight 30–250, measurement 50–150, recovery-day 0–120 and title 1–80 ranges (v1.1 Appendix E); literal ISO text for dates and instants (PostgreSQL's `yesterday`, `now` and `infinity` are rejected); an appointment `timeZone` that must be a name in PostgreSQL's `pg_timezone_names` (the IANA tz database as shipped with the server, case-sensitive, excluding the placeholder `Factory`; the tz data comes from the database host, so a host with older tz data may not know a very new zone); and strict JSON booleans for `completed`, `reminderEnabled` and `privacyMode` (`"true"`, `1`, `null` are rejected, with no Postgres coercion). Error contract: `PT428 consent_required` (no valid current consent for an upsert; never PT401), `PT401` only for authentication/ownership, `PT422 invalid_mutation` for a settings delete (settings are upsert-only), `PT409` for revision/idempotency conflicts. At most one policy per purpose can be current (database-enforced).

Request hashes include `consent_id` on purpose. Phase B invariant: an outbox mutation is **never** rebound to a newly granted consent; after withdrawal and re-grant a genuinely new operation receives a **new** mutation id, and an old applied mutation can only replay with the identical consent id (a changed consent id is `mutation_id_conflict`, with no second side effect). Receipt hashes are deterministic unsalted SHA-256 over the request, so a privileged database reader could infer low-entropy values; this is an accepted internal Phase A residual and a security/privacy review item before any Pregnancy beta or public launch. Notes and outcome notes have no length limit (v1.1 specifies none), so a very large note is bounded only by the transport. The pull returns metadata only (type, id, revision, deleted, sequence); a client reads the canonical row through its owner-only `select`.

## Parity with Pregnancy v1.1 (Appendix A and E, §4.2, §4.4)

Classification: EXACT, NORMALIZED (same domain meaning, platform-shaped) or DEFERRED. There is no unexplained mismatch.

- **PregnancyEntry:** `id`, `method`, `lmpDate`, `conceptionDate`, `dueDateOverride`, `dueDateSource` (user/lmp/scan/clinician), `endedAt`, `outcome` (birth/stillbirth/miscarriage/termination/other/preferNotToSay), `outcomeNotes`, `recoveryEndedAt`, `revision`, `updatedAt`, `deletedAt`, `createdAt`: EXACT in `types/pregnancy.ts` and SQL. The `ended_at`/`outcome` consistency and one-active-pregnancy index are EXACT. `method` is nullable only on a scrubbed tombstone (NORMALIZED, enforced by `pregnancies_active_shape`); Appendix E's `client_mutation_id` column is replaced by the payload-free receipts table (NORMALIZED). The UUIDv4 requirement is client generation (DEFERRED to Phase B; the server accepts any uuid, as Appendix E does).
- **Appointment:** `id`, `pregnancyId`, `startsAt` (timestamptz ISO instant), IANA `timeZone`, `title` (1–80), `notes`, `completed`, `reminderEnabled`, `revision`, `updatedAt`, `deletedAt`: EXACT. The v1.0 date-only appointment is not modelled. Fields are null only on a tombstone (NORMALIZED).
- **Symptom log:** the ten v1.1 symptom values, weight and belly ranges, `date`, `notes`, `revision`, `updatedAt`, `deletedAt`: EXACT. `unique(pregnancy_id,date)` becomes a partial unique index over active rows so a deleted day can be logged again (NORMALIZED; a tombstone's date is scrubbed).
- **Settings:** `recovery_display_days` (default 42) and `privacy_mode` follow Appendix E (range 0–120). The v1.0 §4.4 name `postpartumTrackingDays` with range 14–120 is superseded text (NORMALIZED rename). v1.1 story text also describes `recoveryDisplayDays` per pregnancy, which Appendix A/E do not contain; a per-pregnancy column is DEFERRED and needs a Phase B decision. `revision` and `updatedAt` are sync-envelope metadata.
- **Consent:** `purpose`, `consent_version`, `granted_at`, `withdrawn_at`, `unique(user,purpose,version,granted_at)`: EXACT; length checks and `withdrawn_at >= granted_at` are added (NORMALIZED). The server-owned supported/current policy table is the platform gate. No legal basis or wording is approved here; v1.1 leaves the art. 6 / art. 9 review as a launch requirement.
