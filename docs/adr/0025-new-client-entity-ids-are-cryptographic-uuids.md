# ADR-0025: New client entity IDs are cryptographic UUIDs

## Context

APP-030 requires collision-resistant identifiers generated by
crypto.randomUUID/CSPRNG, with no Math.random entity IDs in new code.
The baseline has ten copies of a timestamp/weak-random generator, eight
timestamp-only creation sites, and a series/month-derived expense instance ID.
APP-029's encrypted cache filenames already use secure randomness, but those
filenames do not determine attachment entity IDs.

## Decision

`core/ids.ts` exports `newEntityId(): string`, delegating directly to the installed
Expo SDK 57 `expo-crypto.randomUUID()` API. All new opaque persistent client
entities, including nested habit logs/subgoals, attachment metadata, savings
contributions and each recurring expense instance, use this helper.

The API returns a cryptographically generated UUID v4. Its native implementation
uses Foundation UUID on Apple and Java UUID.randomUUID on Android; the web
implementation calls Web Crypto randomUUID. Errors propagate. There is no
clock/random fallback, and the helper does not use Expo's getRandomBytes API
(which has a development-only weak fallback).

Generate an entity ID once and copy it into references. A new expense starts a
series with `seriesId = id`. Subsequent instances get new UUIDs and retain that
seriesId, including a legacy root's ID when it lacks an explicit seriesId.
The existing series/month check still prevents duplicate local roll-forward
calls. Trip copies get fresh packing item IDs tied to the new trip ID. CV
selections, attachment owners, savings contribution goals and reminder identifiers
continue to reference their original parent values.

Existing IDs remain opaque strings. Do not regenerate them during hydration,
fetch, update, deletion or backup restore, or require them to match a UUID regex.
Rewriting them could sever existing rows, attachment paths and relationships.
There is no schema or legacy-ID migration. Affected SQL columns are text; nested
IDs and CV selections are JSON. UUID strings pass existing SAFE_SEGMENT checks.

Excluded identifiers retain their contracts:

- Auth/user IDs, server rows, provider/catalogue IDs and participant identities
  are authoritative values supplied by the server, including Profile C data.
- Category and skill-category names are semantic keys and display values, including
  user-entered names; replacing them would lose labels and require a data-model change.
- Seed recipes, default moving checklist keys, modules, enums, routes, translations,
  storage keys, date/week keys and preference composite keys are semantic identifiers.
- Reminder names and UI keys derived from existing identities must remain stable.
- APP-029 cache/temp filenames and ephemeral viewer source tokens retain their
  separate cryptographic generators.

See [the implementation audit](../app-030-id-audit.md) for the complete inventory.

## Consequences

New IDs are clock-independent and collision-resistant across offline devices.
Legacy and UUID records coexist without changing data profiles or persistence
surfaces. Tests guard UUID shape/uniqueness, failure without fallback, creation
flows, references, legacy hydration, attachment upload paths and traversal checks.
Only tests substitute Node crypto for the native Expo module.

Random entity IDs do not enforce business uniqueness across devices. Two offline
clients can independently materialize the same series/month under different IDs;
the current local month check is not a server uniqueness mechanism. Durable outbox,
server mutation idempotency, revisions, tombstones, conflict policy, sync UX,
connectivity policy and migration harness remain APP-031 through APP-038 work.

## Alternatives considered

- Timestamp/counter/Math.random IDs: rejected because clocks and weak randomness
  cannot provide the required security and cross-device collision resistance.
- A new UUID library or hand-rolled UUID: unnecessary; Expo Crypto is installed
  and provides the supported primitive.
- Keeping deterministic series/month entity IDs: does not meet the new entity UUID
  contract. Domain deduplication stays explicit through the existing month check.
- Migrating every existing identifier: risks breaking references, destroys semantic
  identifiers and exceeds APP-030. No migration is required by the specification.
