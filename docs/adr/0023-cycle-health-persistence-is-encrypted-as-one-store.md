# ADR-0023: Cycle health persistence is encrypted as one store

| | |
| --- | --- |
| **Status** | Accepted |
| **Date** | 2026-09-09 |

## Context

APP-028 requires local health state to be encrypted at rest, with an AES-GCM
adapter, a keystore-backed key, raw storage inspection tests and migration from
old storage.

The current cycle Zustand key, `lifesort-cycle`, contains two logical domains:

- `cycle.user-health` - Profile B sensitive health data: cycle dates, symptom
  logs, free-text notes, prediction lengths and reminder preferences.
- `cycle.reference-content` - Profile D reviewed reference content:
  `healthConditions` and `symptomGlossary`.

APP-027 makes the policy rule explicit: a mixed physical surface must use the
strongest protection required by any domain it contains. Because the existing
physical surface contains Profile B data, plaintext AsyncStorage is no longer
acceptable.

Expo SDK 57 provides `expo-crypto` AES-GCM APIs and `expo-secure-store` for
small key-value secrets. SecureStore documentation warns that large payloads can
be rejected by platform limits, so the health dataset itself should not be put
directly in SecureStore.

## Decision

Keep `lifesort-cycle` as one physical Zustand persistence key and encrypt the
entire persisted JSON payload before it reaches AsyncStorage. The encrypted
record is a versioned JSON envelope containing only metadata and an AES-GCM
combined ciphertext. The AES-256 key is generated by `expo-crypto`, encoded as
base64 and stored under `secure-store:lifesort-cycle-health-key` with
`WHEN_UNLOCKED_THIS_DEVICE_ONLY`.

The adapter decrypts only known envelope version 1. Actual absence of the
AsyncStorage key is the only normal "no persisted state" case. Unknown versions,
malformed envelopes, missing keys and authentication failures throw a typed
protected-data error instead of being treated as a new/default store.

The installed Zustand persist middleware can still call `storage.setItem` after
failed hydration when later store mutations occur, so the encrypted adapter also
keeps a narrow per-storage-key write block after protected-data read failures.
That block prevents default state from silently overwriting an existing encrypted
payload. The block is cleared only by a successful protected read, explicit
storage removal or local logout cleanup.

Existing plaintext Zustand payloads are migrated narrowly at read time. If a
legacy `lifesort-cycle` value has the expected cycle-store shape, the adapter
encrypts that exact string and overwrites the AsyncStorage value. Only after the
encrypted write succeeds does the app receive the legacy state. If SecureStore
or the encrypted AsyncStorage write fails, the plaintext source remains in place
for a future retry, but it is not returned to Zustand as an insecure fallback and
subsequent writes are blocked for that storage key.

First-use key creation is serialized with an in-process single-flight promise so
concurrent writers share the same generated AES key. Failed creation clears the
promise and can be retried. Logout/key deletion increments a local key epoch;
in-flight key creation and writes check that epoch and fail rather than
recreating a key after logout.

Logout and account-switch cleanup establish an exclusive encrypted-cycle cleanup
window before persisted Zustand stores are reset. Key deletion alone is
insufficient because Zustand reset calls can launch asynchronous storage writes
that the logout routine does not await directly. During the cleanup window, new
cycle persistence reads, encryption, migration and key creation fail
immediately. New Zustand persistence writes are the one deliberate exception:
they are discarded as resolved no-ops because Zustand's persist wrapper can
launch asynchronous writes from a synchronously used `setState` during the reset
loop. The no-op does not encrypt, read SecureStore, create a key or write
AsyncStorage. Operations that began before the window are invalidated by the key
epoch, and guarded writes remove their just-written value if cleanup started
while the physical write was in flight. The cleanup window waits for active
guarded writes before it releases, then future writes are allowed to create a
fresh key for the next session.

Logout and account-switch cleanup remove the AsyncStorage value through the
existing sweep and delete the SecureStore key explicitly while that cleanup
window is held.

## Consequences

- Sensitive cycle health values are no longer readable as JSON in ordinary
  device persistence.
- Profile D cycle reference content is encrypted too. That is acceptable because
  it shares a physical surface with Profile B data and APP-028 favors the
  smallest robust change over a broader feature rewrite.
- The APP-027 registry remains the policy source of truth and now records the
  extra SecureStore key surface.
- Corrupted or future-version encrypted data fails closed with an explicit
  storage error. A user may need cloud refetch or support if the local key is
  permanently inaccessible, but the app does not leak sensitive plaintext or
  silently replace protected ciphertext with defaults.
- Logout/account-switch cleanup temporarily rejects protected reads, encryption,
  migration and key creation, while dropping new persistence writes. That is
  intentional: it prevents asynchronous reset writes from producing unhandled
  rejections or restoring old encrypted cycle state after the user data sweep has
  removed it.
- APP-029 document-cache encryption, APP-030 cryptographic record IDs and
  APP-038's generic migration harness remain deferred.

## Alternatives considered

**Split the cycle store into separate Profile B and Profile D persisted keys.**
Rejected for APP-028. It would let reference content remain plaintext and cache
independently, but it would require a wider Zustand/state migration for little
immediate benefit. Future E3 work can still split the store deliberately.

**Store the entire cycle dataset in SecureStore.** Rejected. SecureStore is
appropriate for small secrets such as encryption keys; platform limits can
reject large values.

**Keep AsyncStorage plaintext on web.** Rejected for this storage path. APP-028
is about sensitive health data and must not silently fall back to plaintext.

**Return legacy plaintext when migration encryption fails.** Rejected. That
would keep existing users visible during a transient encryption failure, but it
would also normalize plaintext fallback for Profile B data.

**Build a generic encrypted persistence platform for all Profile B domains.**
Rejected as premature. APP-029 and later E3 stories own document caches,
outboxes, record IDs and generic migrations.
